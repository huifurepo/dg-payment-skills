# 异步通知规则

这份文档只保留当前已覆盖支付接口的 `notify_url` 异步通知规则。

本文件只适用于支付和退款交易通知。商户进件通知使用 `$huifu-merchant-onboarding`，不能套用本页协议。

官方通用来源：[异步消息简介](https://paas.huifu.com/partners/start/ybxx/jiekouguifan_ybxx.md)。各接口的具体通知字段仍以对应接口页为准。

控台 Webhook 是另一套平台事件订阅机制，不适用本文件的 RSA 验签和 `RECV_ORD_ID_` 回包规则；Webhook 签名看 `shared-webhook-signing.md`。

## 基本规则

- 聚合下单 `request.data.notify_url` 字段说明中的“异步返回参数”同时指向同一接口页的“聚合正扫异步返回参数”和“聚合反扫异步返回参数”两套通知参数。验签后按通知 `resp_data.trans_type` 与已匹配原订单的 `trade_type` 核对，选择对应数据面；请求/同步的 `trade_type` 不能作为通知中已声明字段读取。正式通知 `trans_type` 为N，缺失时可依据已匹配的落库原交易核对，无法匹配或类型冲突时先查单核对，不能猜字段或类型。不能只实现其中一套，也不能把两套字段合并成一个无场景 DTO。
- 官网接口表把部分 `notify_url` 标为 `N`，只表示协议字段可省略；如果你的生产方案依赖异步通知，该地址仍是上线必备配置。必须由服务端按环境注入真实地址，不能使用官网示例 URL 或把示例当默认值。
- 通知方式：HTTP(S) `POST`
- 编码：`UTF-8`
- 默认超时：`5` 秒
- 重试边界：超时后重试 `3` 次；HTTP `500-599` 默认重试 `3` 次。其他非成功状态会被视为错误，但官方通用页未承诺相同重试次数，不能把所有错误统一写成“最多 3 次”
- 不支持 HTTP 重定向
- `notify_url` 不要带查询参数
- 自定义端口建议落在 `8000-9005`
- 官方通用页关于通知发送侧 HTTPS 主机名/证书校验的历史描述，只说明平台出站通知行为；不得据此让商户接收端、SDK 或主动请求客户端关闭 TLS 证书链、对端或主机名校验

## 收到通知后的返回要求

商户侧收到通知后必须：

1. 返回 HTTP `200`
2. 响应体返回 `RECV_ORD_ID_` + 请求流水号

如果没有按这个格式回包，汇付会继续重试。

## 回调数据体

最容易混淆的点：

- 支付交易类回调，业务数据通常在 `resp_data`
- 商户配置类回调，业务数据通常在 `data`

处理时不要把 `resp_data` 和 `data` 混用。

## 回调验签

- 回调也必须验签
- 验签原文是回调里的业务数据体
- 异步验签不需要再做字段排序
- 这里说的是接口 `notify_url`，使用汇付 RSA 公钥验签
- 控台 Webhook 使用终端密钥 + MD5，不走 RSA

## 幂等要求

同一条异步通知可能会重复到达，业务侧必须做幂等。

建议至少满足：

- 建议建立事件流水表，幂等键至少包含 `huifu_id`、`req_seq_id` / `hf_seq_id`、`notify_type` / `trans_type`、`trans_stat` / `event_type`
- 订单状态更新必须再加业务订单状态锁，核心状态更新成功后才标记事件已处理
- 已处理过且业务状态已安全落地的重复通知才直接返回成功回包

## 状态确认建议

更稳妥的处理顺序是：

1. 收到异步通知先验签
2. 落原始事件并做事件级幂等判断
3. 对核心支付/退款状态调用查询接口做二次确认或补偿查询
4. 通过订单状态锁更新业务状态，成功后再标记事件已处理

特别注意：

- 前端页面回跳不能替代异步通知
- 单次异步通知也不能替代主动查询
