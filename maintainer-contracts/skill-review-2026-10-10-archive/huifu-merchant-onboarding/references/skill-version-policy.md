## 历史阶段记录

以下版本和 SDK 结论只描述对应阶段；旧目标/源码基线不再是当前接入口径。

`2026-09-24` 较早的 Skill 升版阶段：按用户要求将 Skill 升为 `1.0.4`，默认来源同步为 `hfms/1.0.4`，双 Skill 组合为 `hfps/1.3.5;hfms/1.0.4`；支付仍为 `1.3.6`。当时 Python 目标为 `2.0.26`、已核验源码为 `2.0.25`。复用 `2026-09-22` 的34接口、3,367条字段及来源证据，追加版本专属维护记录，不覆盖历史版本事实；该升版不代表已发布。

`2026-09-24` 更早的 SDK 目标调整阶段：按用户要求将进件 Python SDK 目标版本改为 `2.0.26`。当时本地 `../sdk/bspay-python-sdk/dg_sdk/dg_client.py` 声明 `2.0.25`，既有源码/运行探针证据保持原版本，不视为 `2.0.26` 已核验。该阶段将新版差异留 TODO，继续明确部分，不新增开发硬停；Skill 为 `1.0.3`、来源为 `hfms/1.0.3`，支付 Skill 及其 Python SDK 基线未变，未替换 SDK 或改写历史证据。

`2026-09-15` 发布 `1.0.3`：新增电子合同3个、下级权限与统一页面进件3个、微信/支付宝 AT 管理6个接口，共548条新字段路径；同时逐页复审原有22个接口。商户目录新增35、删除11、修改109项合同，净增至2,207条；用户目录总数仍为554，但21项类型、长度、角色或条件文案发生变化。三类来源使用独立锁和目录，历史来源锁不覆盖。

`2026-09-22` 按用户要求同版本更新，Skill 保持 `1.0.3`，来源默认值保持 `hfms/1.0.3`。以用户提供的 Java `3.0.41`、PHP `2.0.31`、Python `2.0.25` 为 SDK 基线；十二个扩展接口仍有九个商户/AT 专属 Request，三个电子合同改为新的 `/v2/agreement/` 路由。本地新增 `V2Invoice*` 类仍指向旧 invoice 路由，必须用已核验的官方 SDK 通用入口调用新精确路径，不允许手写生产 HTTP。官网已解决的旧冲突关闭，未解决的字段、示例、长度或回调冲突按 `onboarding-extension-field-contracts.md` 保留。

该 `2026-09-22` 阶段重新核验安全边界：Java 和 Python 默认执行 TLS 校验；PHP 仍关闭 `CURLOPT_SSL_VERIFYPEER`。按用户同日补充要求，这项既有 SDK 风险仅作非阻断提醒，不设开发/联调代码生成的修复证明前置条件；继续官方 SDK，不能声称风险已修复。字段/协议疑义按 `shared-overview.md` 提醒查阅对应文档、咨询汇付官方或汇付开发者交流沟通群，并用 TODO/配置隔离，继续已明确部分。签验、敏感日志、非法输入和真实操作授权保护不变。图片专用 PHP/Python 缺陷仍未修复，受控例外不扩展到其他接口。

`2026-08-31` 的 `1.0.2` 复审保留为历史发布证据：商户目录当时2,183条，用户目录554条。`1.0.3` 不改写该快照或其组合锁。

`1.0.2` 新增商户多费率配置、配置查询，以及企业/个人用户基本信息修改、用户业务入驻修改和用户列表查询：商户接口分别新增27和17个路径，四个用户新增接口分别新增37、26、120和17个路径，并锁定三语言专属 Request 类、精确路由和 exact-key 扩展约束。

历史 `2026-08-10` 同版本复审确认：当时全部16个接口字段总数和嵌套不变；商户侧三条 `request.data.activated_products` 说明补全 `01=一体化收款产品`，不触发 `1.0.1` 之外的新版本号。

`2026-08-11` 在 `1.0.1` 发布前纠正由历史源码快照误推的 Java/PHP TLS 硬停：常规接口的实际请求必须使用对应官方 SDK，并以门禁禁止 AI 因 TLS 错误前提降级成手写 HTTP+签名客户端；图片接口例外按下一段执行。该修复不改变接口、字段、SDK 版本基线或 `skill_source`，因此版本保持 `1.0.1`。

同日按锁定 SDK 完整发送链路复核图片接口：只有 Java `3.0.40` 的官方专用实现可直接使用；PHP/Python 虽存在生成类或路由，但实现不满足字段、互斥、传输或签验合同。按接入方确认，仅 `/v2/supplementary/picture` 放开保持 multipart、`data` 加签、TLS 和日志边界的通用 POST/自写 HTTPS 降级，不改接口字段或来源标识，版本仍保持 `1.0.1`。

`2026-09-18` 修正 SDK 传输边界表述：官方 SDK 自带的通用调用入口（如 Java `BasePayClient.request(Map, funcCode, ...)`，内部把 `funcCode` 的 `.` 替换为 `/` 拼接 URL）仍走官方签名、验签、请求头与 TLS 主链路，可用于 SDK 没有专属 Request/路由的常规接口（含商户费率查询），不限于图片接口，也不属于受控降级；“仅图片接口允许通用 POST”的例外限制的是离开官方 SDK 的手写实现。该修正不改变接口、字段、SDK 版本基线或 `skill_source`，版本保持 `1.0.3`。

## 更新方式

- Git：拉取维护方仓库后整体替换 `huifu-merchant-onboarding`，重新加载客户端。
- 独立包：用维护方发布的完整新目录替换旧目录，不混合新旧 reference。
- 不知道来源：先确认分发渠道、目标版本和包 SHA。

版本回答必须说明：Skill 不能主动联网检查或推送升级；本地快照不自动代表官网未来最新版。支付 Skill 可独立升级，不要求两个 Skill 使用相同版本号。

`skill_source` 默认值属于本次实际参与生成的 Skill 组合规则：本 Skill 的商户、用户或扩展接口参与时使用 `hfms/1.0.5`；支付与本 Skill 都实际参与当前请求时使用 `hfps/1.4.0;hfms/1.0.5`。仅安装或加载但未参与本次生成的不计入；显式合同值优先并原样透传。
