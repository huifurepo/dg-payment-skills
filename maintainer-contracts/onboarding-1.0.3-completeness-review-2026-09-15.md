# 商户进件 Skill 1.0.3 完整性复查记录（2026-09-15）

## 结论

- 复抓用户指定的35份官方文档，在线正文与本地 `2026-09-15` 活动快照逐字节一致：35/35 相同，官方未在本轮复查期间再次变更。
- 商户、用户、扩展三个字段目录合计34个进件接口、3,309个完整字段路径；字段级独立解析结果与机械生成目录逐节点一致。
- 分账服务的交易分账明细查询仍归支付 Skill；在线 SHA-256 与既有支付来源锁一致，接口合同和 `huifu-pay-integration 1.3.5` 均不变。
- 本轮发现并修复的是 Skill/维护证据遗漏，不是静默“修正”官方冲突。仍未确认的官方矛盾继续保真记录并执行硬停。

## 复查口径

1. 正式参数/出参表是 wire 字段基线；示例独有字段只登记冲突，不进入 DTO。
2. 同时检查路由、请求/响应信封、条件必填、枚举、示例、异步通知、SDK 类、页内表格、外链及页外说明。
3. 字段目录使用机械生成器；商户、用户、扩展分别由独立实现的解析路径逐节点比对字段名、完整路径、方向、中文名、类型、长度、必填、说明、来源 URL 和来源 SHA-256。
4. 历史来源锁只读；本轮只修正当前 `1.0.3` 候选的元数据、reference、测试和证据链。
5. 不调用真实业务 API，不运行真实模型，不提交，不发布。

## 三、仍待官方确认的文档冲突

### 既有商户接口（2组）

1. `request.data.jxf_conf_info.jxf_fee_info.fee_charge_type` 只出现在示例，正式参数表未声明，因此不进入字段目录或 DTO。
2. 商户费率查询 `fee_rate_type` 正式定义为 JSON 数组字符串，但请求示例使用 Python 风格单引号，不是合法 JSON。

### 既有用户接口（3组）

1. 用户业务入驻修改 `response.data` 正式类型为 String，成功示例却渲染为 JSON 对象。
2. 用户业务入驻 `is_priority_receipt` 必填列为 C，P0 说明同时称选填并给默认值。
3. 用户业务入驻修改 `is_priority_receipt` 必填列为 C，说明同时称 P0 必填并描述空值默认。

### 新增扩展接口（12组）

1. 三个电子合同接口的 `resp_code` 正式长度为9，成功示例均为8位。
2. 电子合同列表请求表用 `page_size`，示例用 `pageSize`；响应示例增加未声明分页字段，并用 `create_time` 替代 `createTime`。
3. 电子合同列表若干正式长度短于其枚举/示例，且空列表 wire 没有唯一口径。
4. 下级商户权限配置复用了商户详情响应示例，请求示例还漏掉正式必填的 `data.product_id`。
5. 统一页面进件在成功码长度、URL 长度、异步 `req_date` 长度、`use_chains_flag` 枚举和 `head_huifu_id` 条件必填上存在冲突。
6. 统一页面查询正式字段为 `wx_neal_name_list`，示例为 `wx_real_name_list`；Object/jsonArray 与 String(JSON) 示例混用；`pay_scene` 链接文字和目标锚点不一致。
7. 微信商户配置 `config_type` 长度为1，但枚举使用 `01/02`；成功示例缺少正式 `response.sign`。
8. 微信商户配置查询有一行“必填/长度”列互换、APPID 长度不一致，且成功示例只有内层内容、没有完整信封。
9. 微信实名申请多项正式标 N 的字段，说明中又定义了条件必填场景。
10. 微信实名查询 `qrcode_data` 同时被描述为 base64 图片二进制、可直接加载内容和完整 HTML `img`，wire 不唯一。
11. 支付宝实名申请缺少社会组织主体的 `business_type` 编码，请求示例还违反自身金融机构和地区一致性约束。
12. 支付宝实名查询成功示例缺少正式 `response.sign`。

处理原则：上述冲突均保留正式表值、示例证据和 `[需要官方确认]`；在影响生产 wire、路由、签验或条件必填时不得猜测生成。
